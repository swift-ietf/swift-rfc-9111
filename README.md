# swift-rfc-9111

Use this package when you build an HTTP cache, or a client that honours caching, and need the RFC 9111 decisions: whether a response may be stored, how long it stays fresh, whether a stored response may be reused, how to revalidate it, and what an unsafe request invalidates. It stores nothing itself. The types extend the `RFC_9110.Cache` namespace from swift-rfc-9110. Start from `RFC_9110.Cache.Storage.Eligibility` to decide on storing, `RFC_9110.Cache.Freshness` and `RFC_9110.Cache.ReuseConditions` to decide on reuse, and `RFC_9110.Cache.Validation` to revalidate. For HTTP/1.1 message framing, use swift-rfc-9112.

## Laws

- `RFC_9110.Cache.Storage.Eligibility.isStorable(method:status:control:isAuthorized:hasExpires:isSharedCache:)` checks in this order. Only GET, HEAD and POST are understood. The status must be final. `no-store` refuses. A shared cache refuses `private`. A shared cache refuses an authorized request unless the response has `public`, `must-revalidate` or `s-maxage`. Last, the response needs an indicator: `public`, `private`, `max-age`, `s-maxage`, an Expires field, or a status that is cacheable by default (200, 203, 204, 206, 300, 301, 308, 404, 405, 410, 414, 501). The cache is treated as shared unless you say otherwise.
- The freshness lifetime comes from the first that applies: `s-maxage` in a shared cache, `max-age`, Expires minus Date (never below zero), then, only when heuristics are allowed, a tenth of the time between Last-Modified and Date, capped at one day. Otherwise it is zero.
- The current age follows RFC 9111 section 4.2.3: the larger of the apparent age and the carried Age plus the response delay, plus the time the response has been resident. A response is fresh only while its age is strictly below its lifetime. `RFC_9110.Cache.Freshness.staleDate(control:expires:date:lastModified:responseTime:isSharedCache:allowHeuristics:)` is nil when the lifetime is zero.
- `RFC_9110.Cache.ReuseConditions.canReuse(response:request:age:freshnessLifetime:)` requires validation for `no-cache` on the request or the response, even when fresh. A fresh response also needs validation when it is older than the request's `max-age` or has less freshness left than its `min-fresh`. A stale response needs validation under `must-revalidate` or `proxy-revalidate`. Otherwise a request's `max-stale` allows any staleness when it has no value, and staleness up to its value when it has one. Without `max-stale`, the response's `stale-while-revalidate` allows reuse while a validation runs, which still counts as requiring validation.
- `RFC_9110.Cache.Validation.request(for:from:)` adds If-None-Match from a stored ETag. It adds If-Modified-Since from Last-Modified only when there is no ETag.
- `RFC_9110.Cache.Validation.outcome(of:storedResponse:)`: a 304 keeps the stored status and content and replaces each stored field that the 304 also carries. Any other 2xx replaces the stored response. A 5xx allows the stale response to be served. Every other status is treated as a client error.
- `RFC_9110.Cache.Invalidation.targets(method:status:target:location:contentLocation:)` invalidates only after PUT, DELETE or POST with a status that isn't 4xx or 5xx. The request target is always included. Location and Content-Location are included only when they have the target's scheme, host and port, a missing port counting as the scheme's default.
- Before storing, the hop-by-hop fields and every field named in Connection are dropped. A missing Vary matches every request, `Vary: *` matches none, and otherwise each named request field must be equal in the stored and the current request.
- Reading Cache-Control ignores unknown directives and signed numbers such as `max-age=-5`. A number too large for `Int` is read as 2147483648, as is an Age that large. `max-stale` and `private` without a value are present and distinct from absent. A quoted `private` value is read as a list of field names.
- Expires is written as an IMF-fixdate. A value that isn't a date fails rather than counting as already expired.
